01 · THE TRANSPORT LAYER

The transport layer connects applications

IP moves packets between hosts; the transport layer moves data between applications on those hosts. Port numbers identify the sending and receiving applications. TCP and UDP sit above IP and below application protocols.

Application

Web, video, games, DNS

Transport

TCP or UDP
Ports and delivery behavior

Network

IP addresses and routing

Application data becomes transport segments or datagrams, then IP packets.

02 · TCP CONNECTION SETUP

TCP starts with a three-way handshake

Before data transfer, both endpoints agree to begin a connection and synchronize sequence numbers.

CLIENT (Host A)
SYN →
SERVER (Host B)
01

CLIENT → SERVER

SYN

Client requests a connection and synchronizes initial sequence number.

02

SERVER → CLIENT

SYN + ACK

Server accepts request, acknowledges client sequence, and sends its own sequence number.

03

CLIENT → SERVER

ACK

Client confirms acknowledgment. Three-way handshake complete: Connection Established.

03 · TCP SEGMENT FORMAT

TCP headers carry delivery control

32-BIT ROW FIELD BITS
1 Source Port · Destination Port 16 + 16
2 Sequence Number 32
3 Acknowledgment Number 32
4 Data Offset · Reserved · Control Flags · Window Size 4 + 6 + 6 + 16
5 Checksum · Urgent Pointer 16 + 16
— Options and Padding, if present Variable
FIELD PURPOSE
  • Sending application · Receiving application
  • Order and loss detection (Sequence tracking)
  • Next byte expected from peer (ACK number)
  • Header size, session state & flow control (Window)
  • Integrity validation (Checksum) & urgent data
  • Extends and aligns header on 32-bit boundary
MINIMUM HEADER
20 bytes before the Data/Payload.
AFTER THE HEADER
Data / Payload carries application content.

05 · UDP · USER DATAGRAM PROTOCOL

UDP keeps communication lightweight

UDP is connectionless: independent datagrams need no session.

Low overhead

Small headers and no handshake mean fast setup and instant transmission.

Few built-in guarantees

UDP does not promise delivery, ordering, or retransmission.

Online gaming

Online gaming favors fresh player positions over recovered old updates.

Real-Time Latency Priority Fresh state > Retransmitted stale frames
< 15ms ping

06 · UDP DELIVERY

UDP sends datagrams without retransmission

CLIENT

Send

Datagrams leave independently without prior connection establishment.

DATAGRAM 1  →  ROUTER  →  SERVER ✓ DELIVERED
DATAGRAM 2  →  ROUTER  →  SERVER ✓ DELIVERED
DATAGRAM 3  →  ROUTER  ✕  LOST ✕ DROPPED
SERVER

Continue

No built-in retransmission. The application decides what to do next.

The trade-off: less waiting and less overhead, with less delivery control.

08 · SIDE-BY-SIDE

TCP and UDP make different trade-offs

CHARACTERISTIC TCP UDP
Connection type Connection-oriented (Handshake required) Connectionless (Immediate dispatch)
Reliability and ordering Built in (Guaranteed in-order delivery) Not guaranteed (Best effort)
Acknowledgements Yes (ACK for received segments) No built-in ACK
Retransmission Yes (Automatic on lost/damaged packets) No built-in retransmission
Minimum header 20 bytes 8 bytes
Overhead Higher (Header fields & connection state) Lower (Minimal processing overhead)
Common applications Web (HTTP/S), file transfer (FTP), email (SMTP) Gaming, live media streaming, DNS, DHCP, VoIP

09 · DESIGN CHOICE

Choose
reliability
or low
latency

Start with what the application can tolerate: missing data, waiting, or both.

01

Does every byte need to arrive?

Yes → TCP

Reliable file transfer, database synchronization, and web communication.

02

Is a late update worse than a lost one?

Yes → UDP

Online gaming, live voice/video calls, and real-time audio streams.

03

Is the exchange short and lightweight?

Yes → UDP

Fast lookup queries, DNS resolution, and minimal request-response overhead.
